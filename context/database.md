# Database Architecture & Mongoose Schemas (`MongoDB Atlas 8.3`)

## 1. Plain Concept & Overview
MongoDB is our database. It stores our store catalog, customer orders, user accounts, and audit records. We use Mongoose 9.x in `apps/api` to model our data. Mongoose enforces strict types and validation rules so bad or incomplete data cannot be saved. No customer or order data is stored on Vercel or in the browser; MongoDB Atlas on Render/AWS is our only data store.

## 2. Visual Entity-Relationship Overview

```
 [User] (Admin / Staff)
    │
    ├── creates/edits ──> [Product] (Catalog, Variants, Prices)
    │                         │
    │                    contains items
    │                         ▼
    └── manages ────────> [Order] <─── generated by Customer at /checkout
                           ├── uses atomic sequence from [Counter] ("MIN-1001")
                           └── appends event records to [AuditLog]
```

## 3. Strict Technical Specifications

### Database Rules & Standards
- **Version:** MongoDB Atlas 8.3 (MongoDB Driver 7.4.0, Mongoose 9.7.3).
- **Access Rule:** Only `apps/api` connects to MongoDB. Next.js does not import Mongoose.
- **Timestamps:** Every schema enables `{ timestamps: true }`, automatically managing `createdAt` and `updatedAt`.
- **Primary Keys:** Default MongoDB `_id` is an `ObjectId`, except for `Counter`, which uses a string key (e.g. `orderNumber`).

#### 4. Counter Schema (`apps/api/src/models/counter.model.ts`)
Provides atomic incremental sequences for human-readable order numbers.
```typescript
interface ICounter {
  _id: string; // sequence name: "orderNumber"
  seq: number; // current sequence integer
}

// Atomic generation function:
export async function getNextOrderNumber(): Promise<string> {
  const counter = await Counter.findByIdAndUpdate(
    "orderNumber",
    { $inc: { seq: 1 } },
    { new: true, upsert: true }
  );
  return `MIN-${1000 + counter.seq}`;
}
```

### Database Indexes
Indexes allow fast searches and enforce uniqueness.
| Collection | Fields | Type | Purpose |
| :--- | :--- | :--- | :--- |
| `users` | `email` | Unique | Prevents duplicate user accounts. |
| `products` | `slug` | Unique | Fast lookup for `/products/[slug]`. |
| `products` | `status`, `category`, `price` | Compound | Fast storefront catalog filtering. |
| `products` | `title`, `description` | Text | Keyword search in storefront and admin. |
| `orders` | `orderNumber` | Unique | Fast lookup on receipt and tracking pages. |
| `orders` | `customer.phone` | Standard | Customer order history and order tracking lookup. |
| `orders` | `orderStatus`, `createdAt` | Compound | Admin order dashboard filtering. |
| `audit_logs`| `entityType`, `entityId`, `timestamp` | Compound | Inspection of an entity's history. |

## 4. Beginner Pitfalls & Common Mistakes to Avoid

- **Mistake:** Generating order numbers by counting all orders (`Order.countDocuments() + 1`).
  **Fix:** Under heavy traffic, two orders created at the same millisecond will get the same number. Always use the atomic `Counter.findByIdAndUpdate` sequence.
- **Mistake:** Storing unhashed passwords in MongoDB.
  **Fix:** Never save plain passwords. Always hash them using Argon2 before calling `User.create()` or `user.save()`.
- **Mistake:** Deleting an order from the database when a customer cancels.
  **Fix:** Never hard-delete orders. Change `orderStatus` to `"cancelled"` so financial records and inventory counts stay accurate.
- **Mistake:** Forgetting to index fields that you search or filter by.
  **Fix:** Without indexes, MongoDB must scan every document in the collection. Always define indexes on fields used in `find()` queries.
